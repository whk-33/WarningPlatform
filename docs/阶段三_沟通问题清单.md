# 阶段三三方对齐会 —— 问题清单（2026-11-03）

> 公开文档，团队对齐用。算法侧阶段三实施指南（`_local_notes/阶段三_实施指南.md`）含内部实现细节，不公开。

## 一、后端要回答的 7 个问题（算法 → 后端）

### B1. risk_scores.parquet 放哪，后端怎么找到它？

- **现状**：阶段二产物 `algorithm/data/oulad/processed_full_demo/risk_scores.parquet`（521,488 行 × 9 字段，14 MB）；后端 config.py 没有 processed 探测路径
- **算法约束**：risk_scores 字段契约固定为 `stu_id / course_code / semester / week / risk_prob / risk_level / risk_level_name / pred_event_week / top_factors`（实施指南 §3.2）
- **后端要回答**：探测顺序怎么排？要不要允许 `WP_PROCESSED` 环境变量覆盖默认路径？

### B2. `RiskRepo` 是新建独立类还是混进现有 `Repo`？

- **现状**：`backend/app/data/repo.py` 负责 final_result 聚合，读路径完全不同
- **算法约束**：RiskRepo 只读 parquet，不做训练/校准；进程内 lru_cache(maxsize=1) 一次加载即可
- **后端要回答**：独立类还是合并？

### B3. `GET /api/admin/student/list` 的 risk_level 什么时候切口径？

- **现状**：risk_level 由 `final_result.status`（退学/不合格/良好/优秀）反推；要改成读 risk_scores 的最新一周预测
- **算法约束**：risk_scores 是 16 周逐周预测，产品口径「最新预测为准」，取 `week=max_present`
- **后端要回答**：一次性切换 / 并行开开关 / 还是先改一个新接口让前端对比验收？

### B4. 新增 `/api/risk/*` 5 接口还是给现有接口加参数？

- **现状**：风险周度查询需要 week 参数，现有 admin.warnings 没有 week 维度
- **算法约束**：5 个接口契约（weekly / student / factors / admin/list / admin/stat）见实施指南 §3，字段全部 snake_case
- **后端要回答**：新路由 vs 给现有接口加参数？

### B5. `top_factors` 是 JSON 字符串，后端要不要解析成数组再返回？

- **现状**：parquet 里 `top_factors` 是 `"{\"factor\":\"出勤率\",\"value\":0.00,\"contrib\":0.739}"` 字符串
- **算法约束**：sign 方向修正已在算法侧做完（出勤率这种保护因子不会被列进 top_factors）；`contrib` 总和可能 <100%（被截断时），**不要前端强制归一**
- **后端要回答**：后端解析成数组 vs 透传字符串？

### B6. 后端要不要 subprocess 调算法桥脚本做按需推理？

- **现状**：risk_scores.parquet 只覆盖 OULAD 28,785 学生；新学生/转学生 parquet 查不到
- **算法约束**：`algorithm/src/serving/30_online_risk.py` 已写好，weekly/student/subgraph 三种模式；P95 约 15ms（缓存命中）/ 800ms（新学生）；**后端进程不要 import torch**（多吃 500MB 内存）
- **后端要回答**：subprocess 兜底 vs parquet 查不到直接 404？

### B7. `pred_event_week=-1` 中文展示谁来做？

- **现状**：`pred_event_week=-1` 语义是"本学期内无风险"
- **算法约束**：契约已冻结 `-1` 不是 bug；`week+1` 只在展示层转
- **后端要回答**：后端加 `*_text` 字段 vs 前端自己转？

## 二、前端要回答的 7 个问题（后端 → 前端）

### F1. 16 周曲线：一个接口返回数组 vs 前端循环调 16 次？

- **算法建议**：`GET /api/risk/student/{stu_id}?semester=` 一次返回 16 点数组（性能差 16 倍）
- **前端要回答**：一次返回完整数组 vs 前端循环调？

### F2. 因子条形图颜色按什么映射？

- **算法约束**：contrib 是归一化贡献度（可能 <100%），不要前端强制归一到 100%
- **前端要回答**：颜色方案定了后算法侧不动

### F3. `risk_prob` 0-1 小数，谁转 0-100 百分数？

- **算法约束**：所有预测/校准/阈值计算都用 0-1 概率空间
- **前端要回答**：前端转百分数

### F4. `week` 是 0 起还是 1 起展示？

- **算法约束**：所有 parquet 字段 `week int8 0-15`，不改
- **前后端共同回答**：接口保持 0 起，前端展示层统一 `+1`

### F5. 等级色块颜色方案定了吗？

- **算法约束**：只提供数值 0/1/2
- **前端要回答**：颜色 + 中文映射确认

### F6. 子图可视化：pyvis 还是 echarts-graph？

- **算法约束**：子图 JSON schema 固定（nodes: type/label/risk_level；edges: source/target/weight）
- **前端要回答**：渲染库 + 页面布局（tab 切换 vs 独立页面）

### F7. 周度曲线弹层 vs 独立页面？

- **算法约束**：曲线数据 16 点 + 每点 top 3 因子，JSON 体积可忽略
- **前端要回答**：弹层 vs 独立路由

## 三、共同约束（6 个问题）

### C1. 字段命名统一 snake_case，不转驼峰 —— 三方都同意吗？

阶段一/二字段本来就是 snake_case（`stu_id / risk_level`），没冲突。统一 snake_case，后端省一层转换。

### C2. 新增接口鉴权方案？

- 风险数据是学生敏感信息，**必须**沿用现有 JWT（`Authorization: Bearer xxx`）
- 后端要回答：管理员和学生端各自调各自接口？

### C3. 管理员/学生端两套接口 vs 一套 role 过滤？

- **现状**：student 端接口从 token 取 `stu_id`，不接受前端传参（`deps.py` 的 `self_student_id`）
- **后端要回答**：两套路由 vs 一套 + role 过滤？

### C4. 15% 预警率是硬约束还是可浮动（±5%）？

- **算法现状**：阶段二阈值按 val 集校准到 high 5% + mid 10% = 15% 预警率
- **算法约束**：PSI > 0.25 门禁阻断坏数据，但阈值是否跟着漂移调，需要产品拍板
- **共同拍板**：15% 是目标值，允许 ±5% 浮动；PSI > 0.25 时强制重校

### C5. 实施指南哪些部分公开给前后端？

- **算法建议**：§1 沟通清单 + §3 接口契约 + §9 文件总表 给全组；§5/§7/§8（按需推理/因子公式/PSI 门禁）算法内部
- **三方共同拍板**：公开范围

### C6. 验收顺序：先通接口再可视化 vs 先用 mock 并行？

- **路线 A**：后端写完 RiskRepo + 5 接口 → 算法 smoke → 前端开始写页面
- **路线 B（算法建议）**：前端先用我提供的 risk_scores.parquet 样本 mock JSON 搭页面 → 后端写完接口直接替换数据源。并行度高，mock 字段与 §3 契约完全一致不会返工。
- **三方共同拍板**：验收顺序
