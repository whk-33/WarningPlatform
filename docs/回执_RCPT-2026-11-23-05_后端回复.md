## 五、关于「桥不可用 503」：我们维持 404，但给出可诊断原因

验收方 RCPT-05 里这两行自相矛盾：

- 「降级：子进程非 0 / 超时 / JSON 失败 → 保持 404，并记录 `algorithm_unavailable` 日志」
- 「错误码：学生不存在 404；桥不可用 503」

我们取了前者——**状态码维持 404**，因为改 503 会让前端已有的空态分支失效，而接桥前后行为一致是有价值的。同时在 404 的错误体 `data` 里给出机器可读原因：

| `data.reason` | 含义 |
|---|---|
| `bridge_disabled` | `WP_BRIDGE=0` 或脚本不存在，**根本没尝试推理** |
| `algorithm_unavailable` | 桥跑了但失败（无 torch / 超时 / 非 0 退出 / JSON 坏） |
| `not_found_anywhere` | 离线表没有、桥也正常回了但没这个学生 |

`data.bridge.last_error` = `{"reason": "non_zero_exit" | "timeout" | "spawn_failed" | "error_payload" | "bad_json", "detail": "...", "at": ...}`；成功一次即清空。`/api/health` 的 `bridge` 段同步暴露 `last_error`。

这样「桥挂了」和「这个学生真没有」在排障时一眼可分，前端代码一行都不用改。
