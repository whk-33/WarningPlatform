## 二、通用约定

### 2.1 请求前缀与地址

```
开发环境  http://127.0.0.1:8000
接口前缀  /api
Swagger   http://127.0.0.1:8000/docs
```

### 2.2 认证

```
Authorization: Bearer {token}
```

- 除 `/api/login/*`、`/api/health`、`/api/meta/*` 外，全部需要 token。
- `role` 只有两种：`admin` / `student`。
- **学生端所有接口的 `stu_id` 一律从 token 取**，前端传任何 `student_id` 都不生效，杜绝越权。
- token 有效期 12 小时（`WP_TOKEN_HOURS` 可调），过期返回 `401`。

### 2.3 统一响应

成功：

```json
{ "code": 200, "msg": "success", "data": {} }
```

失败（HTTP 状态码与 `code` 一致，方便 axios 拦截器统一处理）：

```json
{ "code": 403, "msg": "需要管理员权限", "data": null }
```

### 2.4 错误码

| code | HTTP | 含义 | 前端动作 |
|---|---|---|---|
| 200 | 200 | 成功 | — |
| 400 | 400 | 参数不合法（如学期不存在） | 提示 msg |
| 401 | 401 | 未登录 / token 过期 / 账号密码错误 | 清 token，跳登录页 |
| 403 | 403 | 角色越权（学生访问 admin 接口） | 提示 + 回自己首页 |
| 404 | 404 | 学生 / 预警记录不存在 | 提示 msg |
| 422 | 422 | 参数校验失败（缺参、类型错） | 提示 `data[0].field` |
| 500 | 500 | 服务端异常 | 提示"服务异常" |

### 2.5 分页

列表接口统一：

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `page` | int | 1 | 从 1 开始 |
| `page_size` | int | 20 | 上限 100，超出自动截断为 100 |

响应：

```json
{ "list": [], "total": 200, "page": 1, "page_size": 20 }
```

> **注（v1.1）**：`/api/admin/risk/list` 是唯一例外——它沿用阶段四契约冻结的 `{items, total, page, size}`，参数 `size` 与 `page_size` **两个都收**。原因：契约 v1.0 先于本约定冻结、算法侧 mock 已按此字段生成，改动会连带返工。前端封装时把 `items ?? list`、`size ?? page_size` 兜一下即可。

### 2.6 时间与学期

| 项 | 约定 |
|---|---|
| 学期格式 | `2024F`（秋）/ `2025S`（春），`semester` 参数缺省取**最新学期** |
| 学期起始日 | 秋 `09-02`，春 `02-24`（与 `schema.yaml` 一致） |
| 时间格式 | `YYYY-MM-DD HH:mm`，如 `2025-06-09 09:00` |
| 周次 | `semester_week`，`0–15`，`-1` 表示未发生风险事件 |

### 2.7 风险等级

| risk_level | risk_level_text | 含义 | 前端 |
|---|---|---|---|
| 0 | 正常 | 无风险课程 | 绿 |
| 1 | 警惕 | 有课程不合格 | 橙 |
| 2 | 高危 | 退学 / 休学 / 学业警示 | 红 |

> 底层口径来自 `schema.yaml` 的 `label.risk_level`；OULAD 映射为 `Withdrawn→2`、`Fail→1`、`Pass/Distinction→0`。

> **注（v1.1，必须看）**：阶段四 `/api/risk/*` 的文本字段叫 **`risk_level_name`**，取值 **`低 / 中 / 高`**；本文其余接口叫 **`risk_level_text`**，取值 **`正常 / 警惕 / 高危`**。两者 `risk_level` 数值域相同（0/1/2），但**字段名和文案都不同**，是两套已冻结的契约，不要互相映射或统一改写。
> - 前端渲染旧页面：用 `risk_level_text`
> - 前端渲染风险曲线 / 风险榜：用 `risk_level_name`
> - 两套并存是契约 B3 的刻意设计，不是笔误

> **前端已确认（2026-11-17）**：等级文案按上面"两套并存"执行——风险页用 `risk_level_name`（低/中/高），旧页保持 `risk_level_text`（正常/警惕/高危），**同一个图例内不混用**。后端无需改动。


### 2.8 字段命名

- **全部 snake_case**（`student_id`、`risk_level`、`warn_reason`）。
- 前端现有代码里是 camelCase（`stuId`、`warnLevel`），需要改，见 §6。

## 三、业务口径（这份文档最该被 review 的部分）

### 3.1 分析主体

`学生 × 课程 × 学期`。一门课一条 `final_result` 记录；同一个学生在不同学期是不同批次。

### 3.2 `avg_score`（平均分）

```sql
WHERE status <> '退学'            -- 剔除退学
  AND semester = {当前学期}        -- 只取当学期，不跨学期
avg(COALESCE(final_score, 0))     -- 缺考按 0 计入，不拉高均值
```

- 当学期全部课程都是退学 → 返回 `null`（前端显示 `—`），**不要当 0 处理**。
- OULAD 适配后实际只有 `合格/优秀/不合格/退学` 四种状态，`缺考` 不会出现，规则保留给真实数据。

### 3.3 学生级风险聚合

课程级 `risk_level` → 学生级，三个字段各管一件事：

| 字段 | 算法 | 用途 |
|---|---|---|
| `risk_level` | `max(课程级)` | **判定是否预警**，保召回 |
| `risk_score` | `Σ(risk_levelᵢ × creditsᵢ) / Σcreditsᵢ / 2` | **列表排序**，0~1 |
| `high_course_count` | `count(课程级 = 2)` | 优先级，"1 门崩" vs "3 门崩" |

为什么不用纯加权：会稀释单科崩盘（4 门课 1 门挂、3 门及格 → 加权后只是"警惕"），且 OULAD 的 `credits` 是代理值（考核项数量），权重本身不可信。
为什么不用纯 max：会被单门"杀手课"污染，高危名单可能一大半是同一门课的学生。

> ⚠ **预警率提醒**：`max` 聚合会让学生级预警率显著高于课程级。演示数据 200 人里约 60% 学生至少有一门风险课。前端列表建议**默认只看 `risk_level=2`**，"警惕"单独做成"关注"入口。

### 3.4 预警记录（`warn_id` 从哪来）

数据源里没有"预警记录表"，由后端按课程级风险生成：

```
warn_id   = "W" + md5(f"{stu_id}|{course_code}|{semester}|{week}")[:9].upper()
warn_time = semester_start(semester) + week * 7 天（时间取 09:00）
week      = risk_event_time，缺失或 -1 时按 15 处理
```

- **幂等**：同一 (学生, 课程, 学期, 周) 永远得到同一个 `warn_id`，重复跑批不会产生重复记录。
- 只有 `risk_level >= 1` 的课程才生成预警；一个学生多门课风险 → 多条预警记录。

### 3.5 归因来源

模型（HAN/TFT/GNNExplainer）还没训练，`warn_reason`、`factors`、`suggestions` 目前**全部是规则产出**，响应里带：

```json
{ "source": "rule" }
```

GNNExplainer 上线后改成 `"model"`，字段结构不变。**答辩时不要说成"模型解释"。**

### 3.6 图裁剪

| 场景 | 规模 | 说明 |
|---|---|---|
| 管理员全局图 | 默认 50 学生 + 其课程，约 60–70 节点 | `limit_students` 可调，上限 200 |
| 学生个人图 | 本人 + 当学期课程，≤ 10 节点 | 1 跳，不做 2 跳展开 |

`meta.truncated = true` 表示还有更多学生没返回，前端可提示"仅展示风险最高的 N 名学生"。

## 五、接口详情

### 5.1 管理员登录

`POST /api/login/admin`

请求：

```json
{ "username": "admin", "password": "wp123456" }
```

响应 `data`：

```json
{
  "token": "eyJhbGciOiJIUzI1NiIs...",
  "username": "admin",
  "name": "管理员",
  "role": "admin"
}
```

错误：`401` 账号或密码错误（不区分是账号不存在还是密码错，避免账号枚举）。

### 5.2 学生登录

`POST /api/login/student`

请求（`student_id` 填**学号**，不是 `stu_` 内部 ID）：

```json
{ "student_id": "20220100", "password": "wp123456" }
```

响应 `data`：

```json
{
  "token": "eyJ...",
  "student_id": "20220100",
  "student_no": "20220100",
  "stu_id": "stu_100100",
  "name": "学生100",
  "role": "student"
}
```

### 5.3 退出登录

`POST /api/logout` → `data: null`

JWT 无状态，服务端不做失效；前端清 `localStorage.token` 与 `role` 即可。

### 5.4 首页统计

`GET /api/admin/home/stat?semester=2014J&week=8`

| 参数 | 必填 | 说明 |
|---|---|---|
| `semester` | 否 | 缺省取最新学期 |
| `week` | 否 | `0–15`（0 起，前端展示 +1），缺省取默认周（期中第 8 周）。**v1.3 新增** |

响应 `data`：

```json
{
  "semester": "2014J",
  "total_student": 10670,
  "warn_count": 3688,
  "high_count": 2977,
  "mid_count": 711,
  "normal_count": 6982,
  "risk_distribute": { "高危": 2977, "警惕": 711, "正常": 6982 },
  "warn_rate": 0.3456,
  "occurred_count": 2639,
  "occurred_rate": 0.2473,
  "risk_pool_count": 8031,
  "pool_alert_count": 1049,
  "pool_alert_rate": 0.1306,
  "occurred_source": "prob_proxy",
  "week": 8,
  "caliber": "model_week8",
  "caliber_text": "模型风险分 · 第8周 · 学生级 max(课程级)",
  "data_source": "parquet",
  "sample_based": false,
  "record_total": 11260,
  "deprecated_fields": []
}
```

口径：`warn_count = high_count + mid_count`，`total_student = warn_count + normal_count`。

**两层口径（v1.4 补充）**：`warn_rate` 是全表口径。
展示时建议把 `occurred_rate`（`prob` 打满 1.0 的样本，**语义待确认**）和 `pool_alert_rate`（风险池内预警）分开讲，
关系为 `warn_rate = occurred_rate + pool_alert_rate × (1 − occurred_rate)`。
2014J 第 8 周：`warn_rate=34.56%` ≈ `occurred_rate` 的 24.73% + 风险池 13.06%。字段含义见 §5.20，
「已发生」的语义已于 2026-11-23 用 `risk_state` 落实，见 §11.5 末尾。

> **v1.3 变更：本接口不再是规则式期末结算口径。** 它现在内部直接调用
> `/api/admin/risk/stat`，两者同一个数据源、同一个周次、同一个学生级聚合，
> 数字逐项相等。字段名一个没改，前端 `Home.vue` 无需调整。
>
> 旧口径（规则式整学期结算，2014J 实测 `warn_rate=0.5142`）仍保留在
> `AdminRepo.stat()` 中，仅供"期末回顾"类视图调用，**任何首页/看板都不要再展示它**：
> 它没有周维度，本质是考完之后的结算，预警率 51% 也不具备可干预性。
>
> `record_total` 是学生去重前的「学生-课程对」行数，`total_student` 是学生数，
> 两者不等属正常（一个学生选 N 门课就有 N 行）。

### 5.5 学生列表

`GET /api/admin/student/list`

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `keyword` | string | 否 | 学号 / 姓名 / `stu_id` 模糊搜索 |
| `semester` | string | 否 | 缺省最新学期 |
| `risk_level` | int | 否 | 0/1/2，缺省全部 |
| `page` / `page_size` | int | 否 | 默认 1 / 20 |

响应 `data`：

```json
{
  "list": [
    {
      "student_id": "20220100",
      "stu_id": "stu_100100",
      "student_no": "20220100",
      "name": "学生100",
      "major": "计算机科学与技术",
      "class_name": "计科2203班",
      "avg_score": null,
      "has_valid_score": false,
      "valid_course_count": 0,
      "risk_level": 2,
      "risk_level_text": "高危",
      "risk_score": 1.0,
      "course_count": 3,
      "high_course_count": 2
    }
  ],
  "total": 10670,
  "page": 1,
  "page_size": 20
}
```

排序：`risk_level` 降序 → `risk_score` 降序 → `avg_score` 升序（`null` 排最后）。

`avg_score` 口径：剔除退学、缺考按 0、仅当学期。**若某学生当学期所有课程都退学，
剔除后无任何有效成绩，该字段必为 `null`**（2014J 实测 3466 人 / 32.5%，不是缺数据 bug）。

| 字段 | 类型 | 说明 |
|---|---|---|
| `avg_score` | number \| null | 有效成绩均值 |
| `has_valid_score` | bool | `false` 即"全退学，无有效成绩" |
| `valid_course_count` | int | 参与均值计算的课程数，`0` 即全退学 |

前端应判断 `has_valid_score` 决定显示「无有效成绩」还是数字，**不要用 `0` 顶替 `null`**。

### 5.16 单周风险 `GET /api/risk/weekly`

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `stu_id` | string | **是** | `stu_` 前缀内部 ID |
| `course_code` | string | **是** | 课程代码，如 `CCC` |
| `semester` | string | 否 | 缺省取该学生最新有数据的学期 |
| `week` | int | 否 | `0–15`，缺省取第 8 周（期中）；**0 起**，前端展示 `+1` |

响应 `data`（`week=8` 样例）：

```json
{
  "stu_id": "stu_100621",
  "course_code": "CCC",
  "semester": "2014B",
  "week": 8,
  "risk_prob": 1.0,
  "risk_level": 2,
  "risk_level_name": "高",
  "pred_event_week": -1,
  "risk_state": 1,
  "risk_score": null,
  "top_factors": [
    { "factor": "出勤率", "value": 0.44, "contrib": 0.517 },
    { "factor": "课件点击数", "value": 26.0, "contrib": 0.21 },
    { "factor": "测验正确率", "value": 0.0, "contrib": 0.132 }
  ],
  "data_source": "mock"
}
```

字段口径：

| 字段 | 说明 |
|---|---|
| `risk_prob` | **0–1 概率空间**，前端自行转百分数（契约 F3） |
| `risk_level` / `risk_level_name` | `0 低 / 1 中 / 2 高`，直接渲染 `risk_level_name`，前端不要写映射 |
| `pred_event_week` | **`-1` 是语义值**，但**不能无条件读作"无风险"**：`-1` 且 `risk_prob >= 0.5` 时表示"暂无预计周"（推理桥拿不到基线时会回落成 `-1`），只有 `risk_prob < 0.5` 才是"本学期内无风险"。**不要显示成第 0 周** |
| `risk_state` | **v1.7 新增**：`0` = 模型预测，`1` = 事件已发生。为 `1` 时前端显示「已发生」，**不要显示成「风险 100%」** |
| `risk_score` | **v1.7 新增**：未饱和 logit，仅 `risk_state=0` 有值，已发生为 `null`。列表排序用它，详情可不展示 |
| `top_factors[].contrib` | 归一化贡献度，**总和可能 < 1**（被截断），前端**不要强制归一到 100%** |
| `data_source` | 单条记录的来源，同 `/api/health` 的 `risk_source` |

> **默认周次为什么是第 8 周（期中）**：`risk_scores` 的最后一周年限（实测 4 个学期都是 `week=15`）高危率会比前一周突增 20 个百分点以上（2014J：w14 = 31.9% → w15 = 53.3%），因为那一周已接近期末结算，等于「考完才预警」。默认取期中更贴近预警语义，风险榜首页也不会一上来就是半校高危。需要换成别的周：设环境变量 `WP_DEFAULT_WEEK`（重启生效），或前端显式传 `week`。
>
> 上面的示例 ID（`stu_100621`）来自 mock 样本，全量数据下不存在。真实可用的 `stu_id` 从 §5.19 风险榜里取，别写死。

错误：`404` 该学生该课程该周无数据；`403` 学生查别人的 `stu_id`；`422` 缺 `stu_id`/`course_code` 或 `week` 越界。

### 5.17 整学期风险曲线 `GET /api/risk/student/{stu_id}`

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `stu_id` | string | **是**（路径参数） | `stu_` 前缀内部 ID |
| `semester` | string | 否 | 缺省最新学期 |

**一次返回整学期全部周次**（契约 F1：不要前端循环 16 次）。

响应 `data`：

```json
{
  "stu_id": "stu_100621",
  "student_name": "王雨桐",
  "major_name": "数据科学与大数据技术",
  "class_name": "大数据2201",
  "semester": "2014B",
  "course_count": 1,
  "week_count": 16,
  "partial": false,
  "data_source": "mock",
  "sample_based": true,
  "weeks": [
    {
      "stu_id": "stu_100621",
      "course_code": "CCC",
      "semester": "2014B",
      "week": 0,
      "risk_prob": 0.4666,
      "risk_level": 0,
      "risk_level_name": "低",
      "pred_event_week": -1,
      "top_factors": [ { "factor": "课件点击数", "value": 26.0, "contrib": 0.486 } ]
    }
  ]
}
```

- `weeks[]` 长度 = `week_count`，正常情况下 16（0–15）；按 `week` 升序
- 学生有多门课时，每天只保留**当周风险最高的那门**，`course_code` 标明是哪门（与推理桥 `predict_student` 同口径）
- `partial=true`：该学期周次不全（学生中途退课/数据缺失），曲线会断，前端画图不要假设 16 点齐全
- `sample_based=true`：当前跑在 mock 样本上，仅演示用
- `student_name` / `major_name` / `class_name`：**v1.2 新增**，风险数据本身没有这三列，后端从主数据 + `docs/mock_api/student_meta.json` 补；补不到返回 `null`，前端要能显示"未登记"而不是崩。mock 下是**合成数据**，界面上必须保留"演示数据"标识
- `data_source`：`parquet` / `mock` / **`bridge`**（v1.8）。`bridge` 表示这个人不在离线表里，是这次请求现场推理出来的
- `inferred`：**v1.8 新增**（仅 `data_source=bridge` 时为 `true`）。现算结果不落库、不参与风险榜排名，前端若要在页面上加"实时推算"角标就靠它

**推理桥回退（契约 B6）**：`risk/weekly`、`risk/student`、`risk/factors` 三个接口在离线表里查不到时，会调算法侧的 `algorithm/src/serving/30_online_risk.py`（子进程，3 种模式）。桥返回的 16 周里 `risk_score` 一律 `null`（那是离线打分才有的未饱和 logit），`event_occurred` 映射成 `risk_state`。

| 环境变量 | 默认 | 说明 |
|---|---|---|
| `WP_BRIDGE` | `auto` | `1` / `0` 强制开关；`auto` = 桥脚本存在即启用 |
| `WP_BRIDGE_PYTHON` | 后端解释器 | 跑桥的 python，**必须装了 torch** |
| `WP_BRIDGE_SCRIPT` | `<repo>/algorithm/src/serving/30_online_risk.py` | 桥脚本路径 |
| `WP_BRIDGE_TIMEOUT` | `60` | 单次调用超时（秒） |
| `WP_BRIDGE_TTL` | `300` | 结果缓存秒数（失败结果也缓存，避免反复 spawn），`0` 关闭 |

当前是否可用看 `/api/health` 的 `bridge` 字段（`enabled` / `script_exists` / `reason`）。**桥不可用不会让接口变 500**：超时、非 0 退出、JSON 坏掉都统一回落成 404，与 v1.7 行为一致。

错误：`404` 该学生该学期无任何风险数据；`403` 越权。

- 排序（**v1.7 变更，取代 v1.3 的 level 优先**）：**风险池按 `risk_score` 降序**，已发生学生（`risk_state=1`，
  `risk_score` 为 `null`）**整组排在最后**。这样首屏是「还没出事、但模型认为最危险」的人。
  实测 2014J 第 8 周：改前前 20 名**全是已发生**（`prob=1.0`），改后前 20 名全部 `risk_state=0`。
  `risk_score` 与 `risk_prob` 严格单调，缺列时退回 `prob` 排序，顺序等价。
- 粒度：`risk_scores` 是「学生 × 课程 × 周」，一门课一行。本接口已按学生去重，
  **每个学生只出现一次**，`course_code` 是他当前周**最危险的那门课**（level 优先、prob 次之）。
  去重前的行数在 `record_total`（2014J 第 8 周：10670 人 / 11260 行）。
- **`total` 与分档人数和 §5.20 完全对账**：`level=0/1/2` 三次查询的 `total` 相加等于总人数，
  且分别等于 `level_0/level_1/level_2`。这里刻意**保留 level = 学生级 max(课程级)、含已发生学生**，
  与统计同一口径；已发生只是"排在后面 + 带标记"，不从分档里剔除，否则两个数会打架。
- **列表项不含 `top_factors`**（体积考虑）。要归因就点行 → 调 §5.18
- `student_name` / `major_name` / `class_name`：**v1.2 新增**，同 §5.17，补不到为 `null`。有了这三个字段，"本周风险榜"可以独立成表，**不要再拿 `stu_id` 去 join `/api/admin/student/list`**——两套学生 ID 目前零交集（见 §九 限制 10）
- 分页字段是 `items` / `size`，不是 `list` / `page_size`，见 §2.5 注
- `total` 是**过滤后**的总数；mock 下 `total` 来自算法侧导出的全量分布作为"应有规模"参考，
  样本本身只有导出那一周，两者不等属正常（`sample_based=true` 会标出来）
- 时间语义：`week` 是"第几周结束时的预测"，不是"这一周内发生的预警"

### 5.20 风险等级分布 `GET /api/admin/risk/stat`

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `semester` | string | 否 | 缺省最新学期 |
| `week` | int | 否 | `0–15`，缺省取第 8 周（期中） |

响应 `data`：

```json
{
  "semester": "2014J",
  "week": 8,
  "total": 10670,
  "level_0": 6982,
  "level_1": 710,
  "level_2": 2978,
  "alert_rate": 0.3456,
  "occurred_count": 2639,
  "occurred_rate": 0.2473,
  "risk_pool_count": 8031,
  "pool_alert_count": 1049,
  "pool_alert_rate": 0.1306,
  "pool_level_0": 6982,
  "pool_level_1": 710,
  "pool_level_2": 339,
  "alert_rate_combined": 0.3456,
  "occurred_source": "risk_state",
  "data_source": "parquet",
  "sample_based": false,
  "list_available": 10670,
  "record_total": 11260
}
```

- `alert_rate = (level_1 + level_2) / total`，0–1，前端转百分数
- `total` = `level_0 + level_1 + level_2` = **学生数**（**v1.3 修正**：此前是「学生-课程对」的行数，
  2014J 第 8 周曾错报 11260；现在按 `groupby(stu_id).max()` 聚合，与契约 §口径的
  `risk_level = max(课程级)` 一致）
- **`alert_rate` 是"全表"口径**。算法侧 11-17 口径要求把 `prob=1.0` 的样本拆出来单看：

  ```
  alert_rate = occurred_rate + pool_alert_rate × (1 − occurred_rate)
  ```

  | 字段 | 含义 | 2014J w8 |
  |---|---|---|
  | `occurred_count` / `occurred_rate` | `risk_state=1` 的学生（已发生事件，权威字段） | 2639 / 24.73% |
  | `risk_pool_count` | 风险池人数 = `total − occurred_count` | 8031 |
  | `pool_alert_count` / `pool_alert_rate` | **池内**预警人数与预警率，这才是模型表现 | 1049 / 13.06% |
  | `pool_level_0/1/2` | 风险池内的等级分布（与 `level_*` 的差就是被剔出的那批） | 6982 / 710 / 339 |
  | `alert_rate_combined` | 按上面公式还原的全表预警率，应与 `alert_rate` 相等 | 0.3456 |
  | `occurred_source` | 判定依据：`risk_state`（权威字段）或 `prob_proxy`（代理） | `risk_state` |

  前端若只显示一个数，用 `alert_rate`；若要解释"为什么预警率这么高"，
  必须把 `occurred_rate` 和 `pool_alert_rate` 一起显示，否则会被误读成模型误报。

  > `occurred_source=risk_state` 表示读到了权威字段；`prob_proxy` 只在数据缺列时出现
  > （旧 9 列包），此时只能表述为"`prob` 打满 1.0 的样本占比"。11-23 实测两者在 2014J 上
  > 完全等价：已发生行 `prob` 恒 1.0，未发生行最大 0.9989。

- **分母口径（2026-11-23 补充，回应验收 §5.1）**：本接口是「**限定学期 + 按 `stu_id` 去重**」后
  的学生级统计，而算法侧直接对 parquet 按行级算（学生 × 课程），因此同一周会有 0.1–0.2pp 的差：

  | 指标 | 本接口（学生级/限定学期） | 算法侧（行级/同学期） |
  |---|---|---|
  | w8 `alert_rate` | 0.3456 | 0.3468 |
  | w8 `pool_alert_rate` | 0.1306 | 0.1302 |
  | w8 `occurred_rate` | 0.2473 | 0.2490 |
  | w15 `pool_alert_rate` | 0.0031 | 0.0033 |

  两组都满足 `alert = occurred + pool × (1 − occurred)`，**差异属口径不同，不是缺陷**。
  对账时请先按学生级聚合，别拿行级数直接比。

- `record_total` = 聚合前的原始行数，供对账；正常情况下 `record_total >= total`
- `list_available` = 当前列表最多能翻到多少条，**分页器一律用它**
  - 全量 parquet：`total == list_available`（都能翻到底）
  - mock 样本：`total` 是算法侧全量（7804），`list_available` 只有 21，两者不等
- 全量数据实测（2014J / 第 8 周）：`total=10670`、`level_0=6982`、`level_1=710`、`level_2=2978`、
  `alert_rate=0.3456`、`record_total=11260`（去重前）。
  四个学期第 8 周的 **池内**预警率为 16.07% / 15.24% / 18.36% / 13.06%，围绕 15% 波动。
- 预警率口径**已查清**（v1.6，2026-11-23）：34.56% 里包含 `prob` 打满 1.0 的已发生样本。
  parquet 升级 11 列后 `risk_state` 成为权威判据，`occurred_source=risk_state` 已生效，
  可以对外表述为「其中 24.7% 已发生、风险池预警 13.06%」。

错误：`403` 非管理员。

## 十、全量数据接入后的口径变化（2026-11-17）

| # | 变化 | 具体表现 |
|---|---|---|
| 1 | **`week` 缺省值从"最新周"改成第 8 周** | 最后一周年限（week=15）高危率比前一周突增 20pp 以上，等于"考完才预警"。设 `WP_DEFAULT_WEEK` 可改 |

| 5 | **列表与统计的 `total` 是学生数，不是记录数** | v1.3 修正。此前 `total=11260` 是「学生-课程对」行数，`record_total` 现在单独透出去重前的行数 |

## 十一、口径合并与预警率分层（v1.3 / v1.4，2026-11-17）

### 11.1 首页不再有两套数

`home/stat` 与 `risk/stat` 曾差 16.7pp（51.42% vs 34.68%），根源不是算错，是**两件事**：

| | 旧 `home/stat` | `risk/stat` |
|---|---|---|
| 级别来源 | 规则式（成绩/考勤阈值） | 模型 `risk_level` |
| 时间点 | 整学期结算（≈期末） | 第 8 周 |
| 周维度 | 无 | 有 |

期末结算口径本质是"考完之后回头看"，该时点已无干预价值，51% 的预警率也不具备区分度。
v1.3 起 `home/stat` **内部委托** `risk/stat`，字段名一个未改，两者逐项相等。

保留的旧实现：`AdminRepo.stat()`（规则式）。仅可用于"期末回顾"类视图，
**不得再出现在任何首页/看板**。

### 11.2 `risk_scores` 的粒度是「学生 × 课程 × 周」

一门课一行，一个学生选 N 门课就有 N 行（2014J 第 8 周：10670 人 / 11260 行）。
契约里 `risk_level = max(课程级)` 是**学生级**语义，因此：

- `risk/stat`：`groupby(stu_id).max()` 后统计
- `risk/list`：按 `level` 降序→`prob` 降序去重，每生一行，`course_code` 是最危险那门课
- `risk/student/{stu_id}` 曲线：按周取该生最危险的那门课

### 11.3 `risk_level` 由 `risk_prob` 按逐周阈值派生（已查清）

> **本节 v1.3 首版写错过了，此处为更正版。** 首版依据"全局看 `level=0` 的 prob 最高 0.815、
> `level=2` 最低 0.2006"得出"两者不单调、可能来自不同信号"，**结论错误**。
> 错因是跨周混合统计：阈值本身逐周变化，跨周比较把不同的阈值混在了一起。

按 `(semester, week)` 分组后重新验证，**64 个组合全部严格单调**，且
`level = 0 if p < t1 else (1 if p < t2 else 2)` 的复现率为 **100.0000%**：

| 学期 | 周 | t1（0/1 分界） | t2（1/2 分界） | 复现率 |
|---|---|---|---|---|
| 2013B | 8 | 0.7549 | 0.9578 | 1.000000 |
| 2013J | 8 | 0.7547 | 0.9579 | 1.000000 |
| 2014B | 8 | 0.7546 | 0.9583 | 1.000000 |
| 2014J | 8 | 0.7554 | 0.9582 | 1.000000 |
| 2013B | 15 | 0.0926 | 0.2007 | 1.000000 |
| 2013J | 15 | 0.0928 | 0.2006 | 1.000000 |
| 2014B | 15 | 0.0926 | 0.2004 | 1.000000 |
| 2014J | 15 | 0.0926 | 0.2004 | 1.000000 |

由此得到三条必须知道的事实：

1. **阈值逐周变动**：w0–w14 的 t1 在 0.65–0.815 之间浮动、t2 在 0.77–0.985 之间浮动，
   呈逐周抬高趋势。所以**跨周的 `risk_prob` 不可比**，只有同一周内才能比大小。
2. **w15 的阈值是算法侧的 bug，已修**：原 t1≈0.0926 / t2≈0.2004 是在"永不事件"池上取的
   85/95 分位，而该池精确率恒为 0，等于拿永远不出事的样本定阈值。修法是 w15 沿用 w14 阈值
   （0.7600 / 0.9857），模型侧只新增 **0.2%** 预警，该周的高危几乎全是 `prob=1.0` 的样本。
   **我们本地数据还是修复前的版本**，用 w14 阈值重判可得池内预警率 0.31%（2014J）/ 0.09%（2014B），
   与算法侧说的 0.2% 吻合。
3. **`risk_prob = 1.0` 是特殊标记位，不是"概率饱和"**（**本条推翻了 v1.3 首版判断**）。
   算法侧口径：这批行是 `risk_event_time <= week` 的已发生事件，不属于模型预测；
   剔除后才叫**风险池**，池内 `prob` 最大值 0.9981、无一人等于 1.0 —— 这两点我们实测吻合。
   **该语义已于 11-23 落实**：parquet 升级为 11 列，`risk_state=1` 即已发生（`risk_event_time <= week`）。
   11-19 当时只有 9 列、没有 `risk_event_time`，用 `pred_event_week` 反推不成立（2804 行里只有 1 行对得上），
   那段排查记录保留在 §11.5 末尾作历史。

因此预警率要分两层看，不能混成一个数：

```
全表预警率 = prob=1.0 占比 + 风险池预警率 × (1 − prob=1.0 占比)
```

2014J 第 8 周实测：`prob=1.0` 占 24.73%，风险池内预警 13.06%，全表 34.56%（公式还原误差 0）。
**风险池内的预警率才是模型的表现**，四个学期第 8 周分别为 16.07% / 15.24% / 18.36% / 13.06%，
围绕 15% 波动，说明阈值卡位是对的。把 34.56% 当成"模型误报率"是误读。

实现影响：`/admin/risk/list` 与 `/api/risk/student/{stu_id}` 的排序仍以 `risk_level` 为第一关键字。
在同一周内它与按 `prob` 排序**等价**（因为单调），保留 level 优先是为了万一阈值逻辑再变也不会错，
不是因为它俩真的不一致。

### 11.4 `warn/list` 是第三种口径，不能和首页对账

|---|---|---|---|
| `home/stat`、`risk/stat` | 模型 · 第 8 周 · 学生级 | 人 | 3688 |

### 11.5 预警率拆成两层（v1.4 新增字段）

`/admin/risk/stat` 与 `/admin/home/stat` 同时返回下列字段，**`alert_rate` 的语义没变**（仍是全表口径），
新增的是把它拆成两块：

| 字段 | 含义 |
|---|---|
| `alert_rate` | 全表预警率 `=(level_1+level_2)/total` |
| `occurred_rate` | `risk_prob` 打满 1.0 的样本占比（`prob=1.0` 或 `risk_state=1`）。**"是否等同于已发生事件"待算法侧补字段确认，见本节末尾** |
| `pool_alert_rate` | **风险池内**预警率 —— 剔除上述样本后模型新增的预警，对外宣称 15% 应指这个 |
| `risk_pool_count` | 风险池人数 = `total − occurred_count` |
| `pool_alert_count` | 池内预警人数 |
| `pool_level_0/1/2` | 池内三档人数，与 `level_0/1/2` 的差就是被剔出风险池的那部分 |
| `alert_rate_combined` | `occurred_rate + pool_alert_rate×(1−occurred_rate)`，恒等于 `alert_rate`，用于说明拆分自洽 |
| `occurred_source` | `risk_state`（权威字段）或 `prob_proxy`（`prob≥1.0` 推断） |

实测（2014J）：

| 周 | 全表 | `prob=1.0` 占比 | 池内预警 | 公式还原 |
|---|---|---|---|---|
| 5 | 31.16% | 22.08% | 11.65% | 31.16% ✅ |
| 8 | 34.56% | 24.73% | 13.06% | 34.56% ✅ |
| 15 | 57.41% | 51.42% | 12.35% | 57.41% ✅ |

> 前端展示建议：卡片主数字用 `alert_rate`，副标题写「其中 XX% 为 `prob` 打满 1.0 的样本」，
> 或者主数字直接用 `pool_alert_rate` 并注明「模型新增预警」。**别只显示 34.6% 不加解释。**

### ✅ 「已发生」的语义已落实（2026-11-23 更新）

> **结论**：`risk_scores.parquet` 已升级为 **11 列**，含权威字段 `risk_state` 与未饱和排序分 `risk_score`。
> 后端 `occurred_source` 自动切换为 `risk_state`，不必再靠 `prob >= 1.0` 代理。
> 2014J 第 8 周实测：`occurred_rate=24.73%`、`pool_alert_rate=13.06%`、`warn_rate=34.56%`
> （与 9 列代理口径数值一致，说明此前"`prob=1.0` 即已发生"的经验判断在聚合层面成立，
> 但当时确实缺字段级证据）。期末周 w15 风险池预警从 **14.78% 降到 0.33%**（阈值不再取自"永不事件"池）。
>
> **以下 11-19 的排查记录保留作历史**：它说明了为什么只有 9 列时不能对外断言"已发生"，
> 也记录了「用 `pred_event_week` 反推」这个错误方法，避免有人再走一遍。

#### 历史记录：当时为什么不能断言（2026-11-19）

算法侧口头说明「`prob = 1.0` 的行都是 `risk_event_time <= week` 的已发生事件」，
当时本仓库无法核对 —— 导出的 `risk_scores.parquet` 只有 9 列，**没有 `risk_event_time`，也没有 `risk_state`**。

尝试用现有字段 `pred_event_week` 反推，结果**不支持该说法**：

| 2014J 第 8 周，2804 行 `prob=1.0` | 行数 | 占比 |
|---|---|---|
| `pred_event_week <= 8`（若为已发生，应当全在此） | **1** | 0.04% |
| `pred_event_week > 8`（事件在未来） | 825 | 29.4% |
| `pred_event_week = -1`（无事件） | 1978 | **70.5%** |

合理解释是两个字段出自不同模型（`risk_prob` 来自 TFT，`pred_event_week` 来自 DeepSurv），
不能互相印证。此前用 `pred_event_week` 做交叉验证并据此确认「`prob=1.0` ⟺ 已发生」，
**那个推理方法本身是错的**，当时的三条吻合证据只是剔除操作的定义，不构成语义证据。

因此（**仅适用于 11-23 之前的 9 列数据**）：`occurred_*` 系列字段在补导 `risk_state` / `risk_event_time` 之前，
只能当"`prob` 打满 1.0 的样本占比"使用，不得对外表述为"已经出事的学生比例"。
`occurred_source=prob_proxy` 就是这个提示。补字段后代码自动切到 `occurred_source=risk_state`，接口字段不变
——该切换已于 2026-11-23 完成。
